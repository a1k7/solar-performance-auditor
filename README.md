# Solar Performance Auditor

Ever looked at your solar inverter app and wondered whether "11 units today" is actually good? I did too. That's basically why I built this.

It's a small command-line tool that calculates how much your rooftop solar system *should* have generated on a particular day, compares it with what it actually generated, and tries to explain the difference — whether it's dust, heat, shading, an undersized inverter, or something else.

No GUI, no extra libraries, no unnecessary complexity. Just plain Java that runs in your terminal.

---

## Why this exists

My family got rooftop solar installed under the PM Surya Ghar scheme a couple of years ago. After the installation, we were given a login to an app that basically showed one big number — units generated. But there was no way to know what "normal" generation should look like.

If the output dropped by 15% because the panels were covered in dust or a new water tank started creating shade in the afternoon, we probably wouldn't notice.

There are commercial monitoring tools, but many of them are tied to specific inverter brands and mostly just show graphs. I wanted something that could actually explain the problem in simple terms:

"You're 12% below where you should be. It probably hasn't rained recently, so dust could be the reason. You've lost around ₹380 this month."

So I built one. It's not meant to be a perfect solar simulator. It's a practical tool that tries to answer a simple question: **Is my solar system performing as it should?**

## Running it

Clone the repo:

```
git clone https://github.com/a1k7/solar-performance-auditor
cd solar-performance-auditor
```

Compile:

```
mkdir -p out
javac -d out $(find src -name "*.java")
```

Run:

```
java -cp out com.solar.Main
```

There's also a small `run.sh` helper if you don't want to type those commands every time:

```
chmod +x run.sh
./run.sh
```

The repo already includes a sample installation — 3.08 kWp of monocrystalline panels on a south-facing roof, commissioned in May 2022, along with 31 days of plausible readings.

So you can just launch it, choose **3**, and see a diagnosis without entering everything yourself.

## What's in the menu

**1 — Set up a new installation.**
Enter the panel type, number of panels, inverter details, tilt, orientation, commissioning date, and electricity tariff. It takes about thirty seconds.

**2 — Log a reading.**
Enter the date, units generated by the inverter, sunlight level (kWh/m²/day), peak irradiance, average ambient temperature, and whether it rained. The rain information is useful because it helps the tool estimate whether dust may have built up.

**3 — Generate the report.**
This is the main part of the project. It shows expected vs actual generation, deviation, average temperature, days since the last rain, possible causes, and the estimated rupee value of the lost generation.

**4 — View current setup.**
Shows a quick summary of the installation settings.

**5 — Save and exit.**
Saves everything back to the CSV files in `data/`.

All input is validated. If you enter a blank line, a letter where a number is expected, or something unrealistic like 3456 kWh for a 3 kW system, the program will ask you to enter it again instead of crashing.

Run them with:

```
chmod +x test.sh
./test.sh
```

Or manually:

```
mkdir -p out test-out
javac -d out $(find src -name "*.java")
javac -cp out -d test-out $(find test -name "*.java")
java -cp out:test-out com.solar.test.TestRunner
```

Expected output ends with:

```
Passed: 15, Failed: 0
```

The tests don't touch `data/`. They create installations and readings in memory, so running the tests won't affect your saved data.

## How the diagnosis actually works

For every reading, the tool estimates how much DC energy the panels *should* have produced:

```
E_dc = capacity_kW × insolation × tempLoss × degradation × orientationFactor
```

Where:

* `tempLoss` accounts for the fact that panels become less efficient as they get hotter. The cell temperature is roughly the ambient temperature plus a delta based on the panel technology.
* `degradation` represents the gradual yearly loss in panel performance — usually around 0.5% to 1% per year depending on the panel type.
* `orientationFactor` is a simple adjustment for panels that aren't facing south.

After that, inverter efficiency is applied. If it's a string inverter, the code also checks whether the DC output would have gone above the inverter's rated AC power and therefore been clipped.

Once there are enough readings, the tool looks at the overall deviation and runs it through a simple set of rules:

* Within ±3%? Everything's fine. **Healthy.**
* Actual is more than 15% above expected? The data is probably wrong — maybe incorrect units, tariff, or sensor data. **Reading Anomaly.**
* Short by 8% or more and it hasn't rained in 10+ days? **Dust / Soiling.**
* Average ambient temperature above 33°C? **Temperature Derating.** Pretty normal during Indian summers.
* Clipping happens on 20% or more of days? **Inverter Clipping.**
* System is 3+ years old with a 3–12% shortfall? **Gradual Degradation.** Normal aging.
* Day-to-day deviations vary a lot (high standard deviation) with a 5%+ shortfall? **Possible Shading.**

Results are sorted by severity — 3 means serious, while 1 means something worth keeping an eye on.

It's not machine learning. It's a set of rules I wrote based on the common things that can affect rooftop solar performance. If the tool gets something wrong, the logic is all in `Auditor.java`, so it's easy to change.

## About the code

The OOP structure is probably the part I'm happiest with. The project is built around two abstract classes.

`SolarPanel` is abstract. `Monocrystalline`, `Polycrystalline`, and `ThinFilm` extend it. Each panel type has its own temperature coefficient, NOCT delta, and annual degradation rate. The calculations are different, but they all follow the same interface.

`Inverter` is also abstract. `StringInverter` limits its output to the rated AC power — that's how clipping is handled. `MicroInverter` doesn't have the same central bottleneck because each panel has its own inverter.

The interesting part is `Installation.expectedKWh()`. It loops through the panels, calls `dailyOutputKWh` on each one, adds everything together, and then passes the total to `inverter.deliverEnergy(...)`.

Because the classes are polymorphic, adding something like a `Bifacial` panel later wouldn't require changing the rest of the system. I'd just create the new class, and `Installation` and `Auditor` wouldn't need to know anything else about it.

`Reading` is immutable — once you create one, it doesn't change. `Installation` keeps its internal data private and exposes it through getters.

The `Storage` class handles saving and loading the data using two plain CSV files under `data/`.

`readings.csv` stores every reading you've entered:

```

```

Delete either file and the tool starts fresh. Nothing complicated is happening behind the scenes.

## If something breaks

**`javac: command not found`** — Java isn't installed or isn't on your PATH. Install Temurin JDK 17+ from https://adoptium.net/ and open a new terminal window.

**`./run.sh: Permission denied`** — make the script executable once:

`chmod +x run.sh`

**`./run.sh: bad interpreter`** — the file probably picked up Windows line endings. On macOS, fix it with:

`sed -i '' 's/\r$//' run.sh`

On Linux, use the same command without the empty quotes.

**Report says "Reading Anomaly"** — one of your readings is probably physically impossible. Open `data/readings.csv`, find the row with the unusually large `actualKWh` value, and delete it.

**Report says "No readings yet"** — `data/readings.csv` is missing or empty. Restore it from the sample above, or log a few readings first.
